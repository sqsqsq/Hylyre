## Context

基线为 0.5.1，目标为 0.5.2。输入和边界见 [proposal.md](proposal.md)；行为规范见 [screenshot-io spec](specs/screenshot-io/spec.md)。需求方是截图接口消费方，修复责任在 Hylyre。

目前两处对外落盘均直接写原始字节；四处 MIME 判断各自实现，非 JPEG 常被默认当作 PNG。真实 JPEG 离线复现已确认 `.png` 文件和诊断附件实际为 JPEG，垃圾字节也能成功写入。公共 FakeUiDriver 的 PNG 存在 IDAT CRC 错误：`load()` 能读，`verify()` 会拒绝；仅校验文件头或仅完整解码不足以覆盖已知问题。

### 入口盘点与责任边界

| 入口/调用链 | 当前最终写入或返回点 | 本次行为与接线验证 |
| --- | --- | --- |
| CLI `screenshot --out` 一次性 | `loop_cmd.execute_screenshot_file` → `Path.write_bytes` | 先检查后缀，再采集，最后共享保存；实际 CLI 调用验证 |
| CLI `screenshot --session` | 守护 `screenshot_bytes` → 同一文件函数 | 会话传输保持；验证 IPC 分支及守护分发，输出与一次性一致 |
| plan、steps、atomic 的失败诊断 | `failure_diag.capture_failure_boundary` → `.png` 直接写入 | 全部复用共享保存；成功后才登记附件；分别验证调用链 |
| MCP `hylyre_screenshot` 一次性/持久会话 | `server.py` 返回 JSON `mime/base64` | 无对外文件输出；共享 MIME 识别，两条分支均验证 |
| 守护 `screenshot_bytes` | `daemon.py` 返回 `mime/base64` | 无对外文件输出；共享 MIME 识别，既有错误封装不变 |
| CLI 字节函数 | `execute_screenshot_bytes` 返回 `(mime, bytes)` | 共享识别；会话解码后按字节确定 MIME，不将传入 MIME 当真源 |
| VLM 与 agent 视觉方法 | `http_vlm.image_data_url`；agent 传递字节 | 共享 MIME 识别；不改 `screenshot_png` 参数名 |
| Hypium 底层采集 | `.jpeg` 临时文件 → 读字节 → 清理 | 保留驱动接口及采集方式；不把此临时文件当用户输出；确认清理回归 |

`--use-fakes` 的命令桩与测试用 FakeUiDriver 不混为一谈；修正测试假图片不意味着离线命令获得真实设备观测能力。实施时再次搜索 `screenshot`、`capture_screen`、图像扩展名及写入点，交付报告确认无遗漏。

## Goals / Non-Goals

**Goals:**

- 所有按路径输出的成功截图均为请求编码、可完整解码、内容来自本次采集。
- 不支持路径明确拒绝；采集、依赖、校验、编码、写入或替换失败不返回成功、不破坏旧有效目标。
- 所有 MIME 判断使用同一规则；运行依赖可通过发布件实际安装取得。
- 复用既有错误语义、附件协议与 schema 2 发布机制，提供可核对的 A1–A13 验收记录。

**Non-Goals:**

- 不增加图像格式、截图入口、插件注册、状态管理、独立 manifest 或新的错误协议。
- 不改驱动的栅格字节接口、业务步骤、schema 或消费方，不批量修复历史截图。
- 不承诺断电持久性、历史附件不可变存储或并发版本管理；本次保证调用过程中的失败安全与原子替换。

## Decisions

### 1. 公共模块统一规则，不限定恰好两个函数

新增 `hylyre/image_io.py`，供 CLI、API、守护、MCP、VLM 使用，不能依赖 CLI 或具体设备驱动。主要入口为 `image_mime(raw)` 和 `write_image(raw, out)`；后缀解析使用一个小共享函数，使 CLI 能在采集前校验，保存函数也复用同一映射。

后缀 `.png` → PNG，`.jpg/.jpeg` → JPEG，大小写不敏感；保留原请求路径与文件名大小写。不支持或缺少后缀时列出支持范围并抛错，不能改名。CLI 必须在设备连接、截图或 session IPC 前完成该检查。

不选择仅修 CLI 的方案：诊断仍会产生错误文件；不选择把驱动一律改成 PNG：调用方仍可请求 JPEG，也不能解决无效输入和失败覆盖。

### 2. 文件与纯字节接口统一完整校验

`image_mime(raw)` 限定源格式为 JPEG/PNG，先用 Pillow `verify()` 检查结构，再重新打开并 `load()` 完整解码，返回实际格式对应的标准 MIME；未知、空、损坏或截断输入明确失败，不启用容忍截断模式。四处现有嗅探全部收编，VLM 也执行同一规则；MCP 一次性路径可直接使用共享字节函数给出的 MIME，避免重复判断。

`write_image` 复用同一完整校验逻辑。同格式且校验通过时直接保留原字节，避免 JPEG 二次损耗；不同格式才转码。源 MIME 不决定目标格式，也不作为免校验凭据。已知坏 PNG CRC 与截断 JPEG 均进入文件、纯字节接口的反例集。可以用小型内部帮助函数共享已解码结果，避免同一次转码无谓重复解码；不新增缓存、身份层或平行校验规则。

纯字节接口保留有效原字节和现有返回形态，仅在完整图像校验成功后返回 MIME/base64 或构造 data URL。修正 `tests/unit/test_http_vlm.py`、`tests/unit/test_image_data_url.py` 中仅有文件头的成功素材，保留坏图作为明确失败用例。

### 3. 转码保持尺寸和可见内容

不缩放、不裁剪、不用占位图。PNG 输出保留可表示的颜色和透明信息。转 JPEG 时，统一转成 RGBA，在白底合成后转为 RGB 编码；不直接丢掉 alpha。用一张含半透明区域的图片验证此路径，不按来源颜色模式扩建测试矩阵。

JPEG 有损编码不能使用字节相等作为内容验收。使用有色块和空间结构的确定性测试图，对尺寸和解码后的颜色/位置验证；转 JPEG 的质量设置与误差阈值应在测试中明确，避免以过宽阈值掩盖空白或内容错误。同格式保存可断言字节一致，JPEG→PNG 可对源 JPEG 解码后的像素作无损比较。

### 4. 完成临时输出后才提交目标

校验/解码成功后准备输出，在目标同目录创建唯一临时文件；显式指定编码，不能由临时文件后缀推测格式。完整写入并关闭后，使用 `os.replace` 或等价原子替换提交。只有提交成功才返回最终路径。

创建目录、创建临时文件、写入、编码、关闭或替换失败均明确失败；清理本次临时文件，不删除/改写旧目标。Windows 下替换前关闭临时句柄。复用仓库已有“临时写入再 replace”的思路，但不耦合 JSON 专用帮助函数，也不扩建通用事务框架。

诊断路径继续命名 `.png` 并实际输出 PNG，之后才调用 `artifact_from_file`。截图失败由原有异常捕获记录，保持原业务失败和成功 UI dump；目标存在不得作为本次成功依据。不需要改动诊断函数的返回协议。

### 5. 直接声明 Pillow 核心运行依赖

在 `pyproject.toml` 的 `dependencies` 声明兼容项目 Python >=3.10 的 Pillow 范围，并在实施时核实所选版本支持范围。公共诊断和自定义 UiDriver 不必依赖 Hypium extra，因此不只放入 `device` 或 `dev`。

在实际使用图像库的边界加载依赖，使缺失依赖进入既有错误路径，诊断失败不掩盖原业务错误。CLI 继续沿用 ImportError → exit 2，其它异常 → exit 1；错误信息可诊断，失败时 stdout 不输出成功路径。MCP/守护沿用现有异常封装。

不采用 Hypium 间接带入的 OpenCV，不依赖开发机已有 Pillow。干净安装验证分别证明基础源码安装可获得 Pillow，以及 `[device,mcp]` 安装覆盖文档声明的实际入口。

## Risks / Trade-offs

- [额外图像检查与转码成本] → 同格式不重编码；性能数字只报告实测，不承诺“几十毫秒”，不预先引入缓存或基准系统。
- [旧测试依赖坏图或伪文件头] → 修正公共假 PNG 和成功用例素材；坏头/坏 CRC 作为明确反例保留，不降低检查强度。
- [透明转 JPEG 无法保留 alpha] → 固定白底并在发布说明中说明；用一张半透明样例验证。
- [原子替换因权限/文件占用失败] → 返回失败、保留旧文件；覆盖替换失败测试。
- [依赖平台兼容性] → 核实 Pillow 与支持 Python 的交集；在实际发布安装环境记录版本和安装结果，不把本机通过泛化到全部平台。
- [未知签名拒绝改变旧行为] → 变更说明明确旧的 PNG 兜底被移除；现有有效 JPEG/PNG 返回形态不变。

## Acceptance Matrix

编号对应原需求 §六；每项在最终报告记录命令、结果、证据位置，未执行项明确标注。

| 编号 | 验证与通过条件 |
| --- | --- |
| A1 | 真实 JPEG → `.png`：返回请求路径，输出完整 PNG，尺寸与源解码像素一致 |
| A2 | 真实 PNG → `.png`：结构/解码均有效，尺寸内容保留，同格式原字节保留 |
| A3 | JPEG → `.jpeg` 和 `.jpg`：两种路径均正确，完整 JPEG，同格式不二次编码 |
| A4 | PNG → `.jpeg/.jpg`：完整 JPEG，尺寸和图案正确；一张半透明图验证白底策略 |
| A5 | `.PNG/.JPG/.JPEG` 等大小写组合：行为等同小写且不改请求路径 |
| A6 | 空数据、垃圾数据、伪签名、截断 JPEG/PNG、坏 CRC PNG：文件与纯字节接口均明确失败，无成功文件、附件或图像响应 |
| A7 | 无后缀、`.txt/.bmp`：在采集/IPC 前失败，不改名，不产生其它目标 |
| A8 | 编码、临时写入、关闭/替换失败且目标不存在：无半写最终目标，无成功返回，临时文件清理 |
| A9 | 目标原有有效图，本次采集/校验/编码/写入/替换失败：旧字节保持，调用失败，不返回或登记旧图为新成功 |
| A10 | 实际 CLI 一次性/会话，以及盘点出的诊断入口接线：运行真实编码与保存，替身仅放采集或传输边界；不以单测共享函数替代入口验证 |
| A11 | plan/steps/atomic 诊断：附件可解码、哈希对应最终文件；截图失败不掩盖业务失败并保留 UI dump；MCP 两分支、守护和 VLM 的 MIME/原字节/形态正确 |
| A12 | 从实际 schema 2 发布件副本在干净环境安装，不装 dev：基础安装可用 Pillow，实际 `[device,mcp]` 安装入口可用；从仓库外运行图像和适用入口验收，记录导入位置及 0.5.2 版本 |
| A13 | 受影响测试、契约/报告回归和发布门禁通过；设备可用时验证实际截图一次性/会话及解码；不可用则记录未执行和限制，不冒充真机通过 |

测试只替代采集/设备或传输边界，真实图像校验、编码、落盘和附件生成不得被假输出函数替代。故障注入分别覆盖提交前与提交时失败。纯白等合法屏幕不应因为缺少视觉纹理而被当成无效输入；“空白字节流”指缺少有效图像编码，不是业务画面颜色。

## Migration Plan

1. 完成共享模块、调用点、依赖和针对性测试，更新 CLI 帮助、`CHANGELOG.md` 的 0.5.2 段、`README.md` 的推荐版本与版本说明段及兼容边界。
2. 将 `pyproject.toml` 与 `hylyre.__version__` 同步为 0.5.2；保留当前契约 schema 和 package-data。
3. 执行相称的受影响检查；首次整批验收/发布门禁运行完整现有测试，复用有效结果，纯文档返修不重复全测。类型检查使用仓库已有命令；若未配置则如实记录，不为此新增工具链。
4. `python scripts/build_wheel.py --source --clean` 构建 `dist/release-src`；清理前确认目标为预期发布输出目录。`python scripts/build_wheel.py --verify dist/release-src` 校验 schema 2、LF、大小与哈希、源码树指纹。不得手写 manifest 绕过构建。
5. 将发布件 `src` 复制到临时位置再安装，避免 pip in-tree build 污染交付树。在全新 venv 中分别验证基础安装及 `python -m pip install "<源码副本路径>[device,mcp]"`；按需使用文档声明的镜像。使用该 venv 的 Python，从仓库外执行验收，防止本仓源码或 editable 安装遮蔽发布件。必要的测试素材/验收脚本由外部验证目录提供，不要求打入发布件。
6. 再次校验交付树，交付 `src/`、`release.manifest.json`、既有集成文档、0.5.2 变更说明和验收报告；报告列出依赖、入口盘点、A1–A13、版本、tree_sha256、命令及未覆盖项。没有真机证据时可以形成离线验证发布件，但不得称为全部验收或真机兼容性通过。

回退使用原封存的 0.5.1 发布件，不以相同版本替换内容，不改写已产生的截图。未通过的验收项必须在交付报告中显式披露，不能将任务勾为通过。

## 窄修：16位灰度与坏图诊断

有效16位灰度PNG转JPEG时，先将固定输入范围0..65535线性映射到8位0..255，再进入既有白底/RGB编码路径，不按每张图片的min/max自动拉伸。同格式PNG仍保留原字节，尺寸与空间亮度层次保持；RGB、透明和CMYK路径保持。

`_decoded_image` 的图像识别、结构检查或完整解码失败统一提供“截图不是有效PNG/JPEG”的上下文，同时保留具体原始原因和异常链。依赖ImportError继续原样传播到既有CLI exit2；编码、输出写入或替换错误不包装为坏图。失败诊断仍保持原业务失败与成功UI dump。

使用一张含低灰、中灰和高灰空间色块的真实16位PNG验证JPEG亮度/尺寸与PNG原字节；复核坏图CLI stderr、ImportError及I/O分类和诊断不遮蔽。复用首次全量与真机结果，只运行定向检查、重建/验证源码件并从仓库外安装验证最终包。本轮不纳入MPO、POSIX权限或重复校验优化。
